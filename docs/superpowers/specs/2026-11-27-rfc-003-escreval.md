# RFC 003: `escreval`

- **Data:** 2026-11-27
- **Status:** Aceita
- **Relacionados:** [ADR 0018](../../adr/0018-contrato-minimo-de-tipos-pors.md), [RFC 002](2026-11-27-rfc-002-leia-como-expressao.md), [design de evolução sintática inicial do PORS](2026-11-26-pors-syntax-evolution-design.md)

## Contexto

`write()` em `crates/portugol-rs-frontend/src/parser/stmt.rs:582-618` já produz `StmtKind::Write(Vec<Expr>)` em `crates/portugol-hir/src/lib.rs:282`, e os backends já conhecem `Op::Write` e o `print!` do Rust gerado. O design aprovado pede `escreval` com quebra de linha implícita, e o ADR 0018 congela que `escreval(a, b);` é somente açúcar para `escreva(a, b, "\n")`, sem tipo ou opcode novo. Esta RFC fixa o contrato observável no frontend, HIR, bytecode/VM, Rust gerado, IDE e playground, sem alterar `escreva`.

## Decisão

### Sintaxe e equivalência

1. `escreval` é um comando com a mesma lista de argumentos de `escreva`, terminada por `;`. A equivalência é exata: `escreval(a, b);` ≡ `escreva(a, b, "\n");`.
2. `escreval();` ≡ `escreva("\n");`: sem argumentos, a única saída é a quebra de linha.
3. Parênteses e `;` são obrigatórios. `escreval` não é expressão, não produz valor e não é aceito em posição de expressão.
4. A conversão e a escrita de cada argumento seguem a regra atual de `escreva`; não há especificador de formato novo. `leia()` continua com tipo `cadeia` fixo, conforme RFC 002 e ADR 0018, e chega a `escreval` como cadeia, sem conversão.
5. Não há deduplicação de quebras: um `"\n"` escrito pelo programa é argumento como qualquer outro. `escreval("olá\n")` termina com duas quebras de linha, e `escreva` permanece exatamente como é hoje.

### Lowering, HIR e spans

1. O frontend, ao converter o comando em HIR, acrescenta uma cadeia `"\n"` sintética como último argumento do `StmtKind::Write(Vec<Expr>)` resultante. Não há novo `StmtKind`, novo nó de HIR, novo tipo, novo `Op` ou novo opcode; o resultado é o mesmo da chamada equivalente a `escreva`.
2. A cadeia sintética tem span de largura zero, `[p, p)`, em que `p` é o offset de bytes imediatamente antes do `)` de fechamento de `escreval(...)`. Nenhum byte do fonte pertence a esse argumento, que não deve ser alvo de diagnóstico próprio. Os argumentos escritos no fonte mantêm seus spans originais.
3. Spans são offsets UTF-8 semiabertos `[início, fim)` em bytes, inclusive com acentos. Source maps, bytecode/VM e Rust gerado usam o mesmo mapeamento: o `\n` sintético é atribuído ao comando, não a um trecho inexistente do código.

| Trecho (coluna 0) | Span do último argumento escrito | Span do `\n` sintético |
| --- | --- | --- |
| `escreval("Olá");` | `[9, 15)` | `[15, 15)`; `á` ocupa 2 bytes |
| `escreval(a, b);` | `[12, 13)` | `[13, 13)` |
| `escreval();` | — | `[9, 9)` |

### Bytecode, VM e Rust gerado

1. O backend continua emitindo `Op::Write` com a lista de argumentos já acrescida do `\n`; não existe `Op::WriteLine` e não há VM nova.
2. O exportador Rust continua emitindo `print!` com os mesmos argumentos, inclusive o `\n` sintético. `escreval` não vira `println!`, não cria helper novo e não muda a ordem de escrita.
3. Os limites de saída existentes continuam valendo para a quebra sintética como para qualquer argumento de `escreva`. VM e Rust gerado produzem stdout idêntico; não há campo JSON, fachada ou API WASM nova.

### IDE e playground

1. `escreval` é `builtin` na IDE e no playground, no mesmo grupo de `escreva` e `leia`. Não é `keyword`, não é palavra reservada e não entra na tabela de keywords. O contrato completo de realce é da RFC 006.
2. Completions e ajuda documentam `escreval` como forma abreviada de escrever com quebra de linha. O realce é apenas apresentação e não altera o documento.

### Fronteiras

- Interpolação de cadeias é decidida na RFC 004 e retorno implícito na RFC 005. Esta RFC não define `"{nome}"` nem expressão final de bloco sem `;`; `escreval("Olá, {nome}!")` só interpreta a interpolação quando a RFC 004 for implementada.
- `escreval(leia());` usa a leitura com tipo fixo `cadeia` da RFC 002 e acrescenta apenas o `\n`; nenhuma conversão de entrada é introduzida aqui.
- Não há nova crate, renomeação de produto, pasta `specs/` paralela ou API WASM. RFCs e design docs continuam em `docs/superpowers/specs/` e ADRs em `docs/adr/`.

## Exemplos válidos

```pors
funcao inicio() {
    escreval("Olá, ", "mundo!");
}
```

stdout esperado: `Olá, mundo!\n` — uma linha terminada em `\n`, sem espaço ou byte extra.

```pors
funcao inicio() {
    escreval();
}
```

stdout esperado: `\n` — somente a quebra de linha.

## Exemplos inválidos

| Trecho (coluna 0) | Motivo |
| --- | --- |
| `escreval(a, b)` | falta o `;` do comando |
| `seja x = escreval("a");` | `escreval` não é expressão e não tem valor |
| `escreval a;` | falta o `(` da lista de argumentos |

## Consequências

- Para qualquer lista de argumentos, VM e Rust gerado devem produzir exatamente o stdout da chamada equivalente a `escreva(..., "\n")`.
- Os testes de aceite devem comparar saída observável, spans UTF-8 em bytes e a classificação `builtin` de `escreval` na IDE e no playground.
- Qualquer mudança nesta equivalência, no span sintético ou na classificação do nome exige revisão desta RFC e do ADR 0018 antes de entrar em código.
