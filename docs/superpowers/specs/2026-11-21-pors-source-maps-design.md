# Design: source maps for Portugol-to-Rust

## Intent

Make generated Rust useful as an educational bridge: every generated region that
has a trustworthy origin points back to the `.por` or `.pors` source, and
`rustc` errors can be shown at the corresponding source location. This builds
on the current shared typed HIR and Rust emitter; it does not add a competing
parser or type checker.

## Current state

- `portugol-hir` carries UTF-8 byte spans on statements, expressions, and
  bindings.
- `crates/portugol-rust/src/codegen.rs` renders one `String` and discards those
  spans.
- `portugol-service::RustExport` returns generated code or one localized source
  diagnostic, without source mappings.
- The IDE's Rust preview is read-only text. PORS execution compiles generated
  Rust and currently displays compiler stderr, which refers to a temporary
  `.rs` file rather than the user's document.

## Goals

- Emit generated byte ranges mapped to original byte ranges, with explicit
  quality (`exact`, `approximate`, or `generated_only`).
- Keep source positions anchored in UTF-8 bytes in Rust; convert to CodeMirror's
  UTF-16 offsets at the service boundary.
- Parse structured `rustc` JSON diagnostics, map primary generated spans back to
  the original document when possible, and preserve the original compiler
  message for expert detail.
- Present mapped errors in the existing IDE diagnostics flow and let students
  navigate from a mapped Rust preview region to its source.
- Discard asynchronous results when the source tab or revision changes.
- Support the shared exporter for both classic Portugol and Portugol-RS without
  changing their language semantics or existing save/detach behavior.

## Non-goals

- No claim that all Rust diagnostics can map to a single source expression.
- No source rewriting, automatic fixes, new language constructs, or ownership
  simulation in this feature.
- No execution of user-authored `.rs` files.
- No change to the classic Portugol interpreter or debugger.

## Approaches considered

1. **Keep rendered compiler text only.** Lowest implementation cost, but users
   still have to interpret a temporary Rust file and generated line numbers.
2. **Add a second Portugol-RS analyzer for compiler failures.** Could produce
   localized messages, but would duplicate Rust's type and borrow rules and
   drift from the actual compiler.
3. **Carry HIR spans through code generation and consume structured `rustc`
   diagnostics.** Chosen: the existing HIR remains the semantic authority,
   mapping is explicit, and unmappable compiler output stays labeled as
   generated-only instead of being guessed.

## Design

### Mapping model

The Rust emitter will return generated source plus mapping segments. A segment
contains half-open generated and original byte ranges, and a quality value.
Mappings are recorded for statements, identifiers/bindings, and expressions;
when segments overlap, consumers choose the smallest enclosing mapped segment.
Emitter boilerplate without an originating source span is `generated_only`.
The map is deterministic and tied to the exact source revision used for
generation.

`exact` means the generated range comes directly from one HIR binding,
expression, or statement span. `approximate` means generated expansion or
boilerplate can only be associated with the containing source statement.
`generated_only` means there is no defensible source range. Selecting a mapped
diagnostic is an explicit navigation action; approximate results must display
their quality label before navigation, and generated-only results stay in the
Rust preview.

### Service contract

- Extend Rust export results with a source-map payload while keeping the
  existing `code` and `diagnostic` fields intact.
- Convert original byte ranges to UTF-16 editor offsets using the existing
  position conversion utilities. Generated offsets remain UTF-8 byte offsets.
- Compile with `rustc --error-format=json` and parse each diagnostic record
  without invoking a shell. Map the primary span through the source map; retain
  rendered compiler detail and the generated location when mapping is absent.
- Represent the command result as a tagged outcome: `executed` carries runtime
  stdout, stderr, and exit status; `compile_error` carries mapped diagnostics
  and raw compiler stderr. A compiler rejection is a successful IPC response
  with a typed outcome, not a transport failure. Runtime fields keep their
  existing meaning.
- Ignore malformed or unknown JSON records safely and preserve raw stderr as
  fallback detail.

### IDE behavior

- Show mapped compiler errors in the existing Messages panel and mark the
  original source range; selecting a diagnostic navigates to that span.
- Keep raw `rustc` wording available in the diagnostic detail.
- Render mapped portions of the Rust preview as safe text nodes with accessible
  navigation back to the source. Do not use generated text as HTML.
- If a range cannot be mapped, identify it as generated Rust and do not move the
  source cursor to an approximate position without labeling that quality.
- Apply the existing stale-response guards to export, compile, and diagnostic
  responses.

The frontend owns revision identity: capture the active tab and immutable
CodeMirror document state when starting each request, increment the existing
generation token for export refreshes, and discard the entire response if the
tab or document has changed. No revision token is persisted or trusted across
the Rust service boundary.

### Compatibility and safety

- Existing consumers may ignore the additive source-map field.
- Classic runtime and PORS supported syntax remain unchanged.
- `rustc` remains a fixed executable with fixed arguments and the existing
  temporary-directory lifecycle; no shell, Cargo, or arbitrary `.rs` execution
  is introduced.
- Compiler diagnostic parsing is bounded by the existing source limit and
  stderr captured for a single invocation.

## Verification

- Unit tests for map ranges, nested/overlapping selection, Unicode conversion,
  and generated-only fallback.
- Tests using rustc JSON fixtures for mapped primary spans, no primary span,
  unknown fields, and malformed records.
- An end-to-end service test that runs supported source and confirms the map
  uses the exact source revision.
- Frontend tests for diagnostic navigation, preview mapping, and stale results.
- Run the workspace's relevant Rust, frontend, desktop, and cross-platform CI
  gates; retain existing Portugol output-equivalence tests.

## Calls left to implementation

- Choose compact Rust structs and serialization names consistent with existing
  camelCase IPC types.
- Keep mapping segments ordered and deterministic; deduplicate only when
  semantics are unchanged.
- Prefer narrow statement/expression ranges over broad file-level guesses.
