# FERRO-Only Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Work in isolated worktrees, use TDD for product changes, request review before merging, and keep each PR green.

**Goal:** Port the product's retained language and learning features to `.fer`/Rust, then remove `.por`/`.pex` support behind an explicit acceptance gate.

**Architecture:** Keep the Rust + Tauri desktop shell. Expand the independent FERRO frontend and shared HIR; support both correct Rust generation for normal runs and HIR-to-bytecode for VM debugging. Retain the shared VM while retiring classic-only parser, semantic analyzer, compiler, examples, exercises and command paths only after their replacements pass.

**Tech Stack:** Rust workspace, Tauri 2, TypeScript, CodeMirror 6, `rustc`/Cargo, existing Node and Rust test suites.

**Spec:** `docs/superpowers/specs/2026-11-22-ferro-only-product-design.md`; accepted decision: `docs/adr/0016-ferro-como-linguagem-autoral-e-retirada-do-por.md`.

## Global Constraints

- Product name and Rust + Tauri architecture remain unchanged.
- `.por`/`.pex` continue to work until their replacement gates are met; do not remove them early.
- `.fer` is an authored educational language, not a claim of full `rustc` compatibility.
- Normal FERRO execution uses Rust generation; FERRO debugging uses the shared VM unless an explicit architecture decision changes that.
- Never present ownership simulation as a real trace; associate explanations with the active source revision.
- Keep the frontend from invoking arbitrary shell commands; preserve process supervision, limits and explicit consent.
- Do not sign commits/PRs with coauthorship or “Generated by” trailers.

## Review Focus

- New grammar compiles in the VM but diverges from generated Rust — each task adds differential behavior tests.
- Unsupported syntax falls through to classic `.por` parsing — add strict language routing tests before changing detection.
- Collection/function semantics exceed runtime bounds — test time, output, memory, cancellation and recursion/instruction limits.
- Rust concepts are shown editorially as runtime truth — require `rustc` comparison or clear simulation provenance.
- Legacy removal deletes shared VM behavior or user files — use consumer searches and keep deletion as the final isolated task.

## Stage 1 — Expand FERRO language semantics

Deliver separately reviewed PRs per coherent language feature. Each feature first adds failing parser/semantic/runtime tests, then HIR, frontend diagnostics, VM lowering, Rust code generation and differential tests as applicable.

### Task 1.1: functions, parameters and return values

**Likely files:** `crates/ferro-hir/src/lib.rs`, `crates/ferro-rust-frontend/src/{lexer,parser}.rs`, `crates/ferro-bytecode/src/ferro.rs`, `crates/ferro-rust/src/`, `crates/ferro-service/tests/`.

Acceptance: declarations and calls, typed arguments/returns, scope/shadowing, recursion policy, source spans, debug frames and generated Rust agree for tested cases.

### Task 1.2: collections and iteration

Acceptance: typed vector/matrix or selected Rust-style collection API, indexing/bounds, ownership/copy/clone policy, limits and differential tests are explicit.

### Task 1.3: remaining control flow and expression operators

Acceptance: matching/patterns and selected classic flow constructs have declared semantics, exhaustiveness diagnostics and consistent VM/Rust behavior; unsupported constructs report localized FERRO diagnostics.

### Task 1.4: Rust-inspired compound types

Acceptance: structs/enums, `Option`/`Result` and pattern matching have educational semantics and real generated Rust; unsupported generic/lifetime behavior is explicit.

## Stage 3 — Port libraries and IDE workflows

Port each library family from `docs/PARIDADE.md` in a separate testable slice, documenting API, effects, limits, VM/debug behavior and Rust implementation. Port the IDE features that remain useful to FERRO/Rust: completion, hover/help, formatting, outline, rename, source maps, workspace, files, graphics/input/audio and project execution.

## Stage 4 — Replace classic learning content

Define a versioned FERRO exercise format and runner before changing frontend import or progress. Add FERRO/Rust examples, help and curriculum. Every exercise must have real cases and progress only on full pass; keep `.pex` until the catalog and imported exercise workflow are replaced.

## Stage 5 — FERRO/Rust by default

Make new files `.fer`, make language detection strict, add `.fer` CLI workflows, migrate file dialogs, workspace, OS associations and export. Test unknown extensions and reject `.por` explicitly at the cutover.

## Stage 6 — Remove classic implementation

Only after all matrix and learning-content gates pass, remove `.por`/`.pex` production routes, Tauri commands, CLI classic behavior, classic parser/semantic/compiler crates without consumers, fixtures/assets/corpus and associations. Verify the shared bytecode/VM path remains and FERRO debugger tests still pass. Update user docs, credits and release notes; retain the existing product name and `v0.x` line.

**Final verification:** Rust workspace tests and Clippy, desktop frontend tests/build/typecheck, Tauri tests/build on Linux/Windows/macOS, Linux/KDE smoke, CLI FERRO/Rust tests, file association/unknown-extension tests, and repository search proving no user-facing `.por`/`.pex` support remains.
